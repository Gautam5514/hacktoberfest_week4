# Securing and rebuilding The Last Commit

The Last Commit builds and type-checks cleanly, but it is a demo-grade prototype whose headline features are not wired in, and its riskiest code is the part that touches the user's disk and shell. **Two critical security defects chain together**: `POST /api/repositories` accepts any `localPath` that exists (`repositories/route.ts:19-30`), and `POST /api/patches/[id]/verify` then runs that directory's `test.js` through `exec` with the full server environment (`resurrection.ts:151,169,232-234`). The "deep AST analyzer" (`src/lib/ast-analyzer.ts`) and the "Mastra workflow" (`src/lib/mastra/index.ts`) are imported by nothing, and the Mastra layer is a hand-rolled class with no `@mastra/*` dependency, yet the README and DEV_SUBMISSION advertise both. The patch generator is regex-based and emits broken code for `fs.exists` and `crypto.createCipher`, and it can fabricate a fake `package.json` diff. Persistence is a synchronous, non-atomic, whole-database JSON file that overwrites itself with seed data when it fails to parse. Next.js 14 is unsupported and the October 2026 security fixes shipped only for 15.5.x and 16.4.1 ([Next.js security update](https://nextjs.org/blog/nextjs-security-update-october-14-2026.md)). The ideal design is a real Mastra workflow over one shared TypeScript Program, validated edits, a scrubbed sandbox, an atomic store, and Next 16. The fix plan below orders the work by severity, then effort.

## The architecture is a JSON-file hub with two dead modules

All state flows through a single in-process store, `src/lib/store.ts`, which persists the whole database to `process.cwd()/.lastcommit_data.json` (`store.ts:17`). API routes call the store, and the store calls `scanner.ts` for autopsies and `resurrection.ts` for patches and verification. The chat route calls `ghost-ai.ts` directly, which posts to a local Ollama `gemma3:4b` with a 6 second abort and falls back to keyword-matched canned replies on any failure (`ghost-ai.ts:60-82,112-138`). The only analyzer actually used is `scanner.ts` (406 lines), which counts lines of code, applies manifest checks and runs regex scans for deprecated Node APIs and broken relative imports. The TypeScript-compiler visitor in `ast-analyzer.ts` (194 lines) has one importer, the unused `mastra/index.ts` (242 lines, 4 plain-object "tools", 5 stage methods, zod schemas that validate nothing). Together that is roughly 440 lines of shipped dead code.

The front end is eight `'use client'` page files that each fetch `/api/repositories/${id}` in a `useEffect` (for example `lab/[id]/page.tsx:36-37`, `autopsy/page.tsx:29-30`, `report/page.tsx:31-32`), with no shared `lab/[id]/layout.tsx`. The build output confirms the lab routes are server-rendered on demand yet get no SSR data benefit. That GET is not a pure read: it can trigger a full autopsy, generate a patch and persist the database (`route.ts:15-18`, `store.ts:244-257,283-288`), and it returns full patch contents on every tab switch. `CodeExplorer.tsx` (171 lines) and `DiffViewer.tsx` (181 lines) are the two components in scope. `LabTabs.tsx` is purely presentational.

Verified state: `npx tsc --noEmit` exits 0, and `npm run build` compiles with 8/8 pages, 87.3 kB shared first-load JS and a largest route of 102 kB, on Node 24.3 and Next 14.2.35. That cleanliness overstates safety. The code has 19 `any` occurrences, empty `catch` blocks swallow errors (`store.ts:132-134,143-145`, `scanner.ts:103-105,340-342`, `resurrection.ts:58-60,114-116`), and no ESLint config exists, so linting is effectively off. There are no automated tests of `src/`. `scripts/test-resurrection.js` only runs `node test.js` in the example repos and counts 12 files. Separately, `.browserslistrc` is deleted in the working tree but present at HEAD. Browserslist throws when both that file and a `package.json` key exist (`node_modules/browserslist/node.js:443-446`), and both hold the identical query `defaults`, so the deletion is correct and should be committed. The audit did not confirm that the committed duplicate fails `next build` on a clean checkout.

## Critical and high defects cluster in file access, execution and patch correctness

**Security.** The import route performs no allow-listing, authentication or schema validation (S1). Pointing `localPath` at `/` or `~` lets `/files?file=` read anything the server can read (`files/route.ts:25-34`) and makes the synchronous scan walk the whole disk. Verification is arbitrary code execution (S2): the "sandbox" is a copy under a predictable `/tmp/last-commit-sandbox-<ts>`, with no container, user separation, network block or resource limits, and the baseline test runs directly in the real repository. The containment check is `startsWith(path.resolve(workspacePath))` with no trailing separator (`files/route.ts:27`, `mastra/index.ts:90`), so `/ws/app` admits `/ws/app-secrets/x`, and symlinks are never resolved (S3). Settings are mass-assigned from an unvalidated body (`settings/route.ts:42-43`, `store.ts:346-349`), so an attacker-chosen `ollamaEndpoint` becomes an SSRF target fetched on every settings read and chat call (S4), even though `zod` is installed. `copyRecursiveSync` follows symlinks and can loop (`resurrection.ts:244-258`), error responses leak `error.message` with absolute paths, and the verify route derives the repo id with `id.split('_')[1]`, which breaks for `repo_abc123`-style ids (S7, not reproduced). `npm audit --omit=dev` reports 4 vulnerabilities (1 critical, 2 high, 1 low) touching `next`, `postcss`, `diff` and `zod`, with fixes requiring next 16 and zod 4; the full advisory text was not captured. The committed `.lastcommit_data.json` embeds the author's absolute path (S9). The localhost-only caveat matters: the audit read code but never started the server, and exposure depends on deployment.

**Patch correctness.** The patch generator misleads about what it fixes. The `fs.exists` rewrite emits `const exists = fs.existsSync($1);\n  (($2) => {` and leaves the callback body in an uncalled arrow function (`resurrection.ts:84`). The `createCipher` rename to `createCipheriv(` supplies no key or IV, so it throws at runtime while the summary claims it "Replaces deprecated Buffer/crypto constructors" (`resurrection.ts:87,135`). When nothing matched, a fabricated `revival-target` `package.json` and a diff with a wrong hunk header are produced (`resurrection.ts:120-129`), and the sandbox then overwrites the real manifest with it (`162-166`), so a "passed" verification can run against a replaced manifest. The `new Buffer(` regex fails on nested parentheses and also matches comments and strings (`resurrection.ts:81`). The deprecated-API detection has its own false positives: the engine check `engineSpec.includes('8')` flags `>=18.0.0` and `^20.14` as outdated (`scanner.ts:125`) and feeds the health score, and `querystring`, a Node built-in, is listed as a deprecated npm dependency (`scanner.ts:20`). The `.tsx`/`.jsx` files get the wrong `ScriptKind` and parse diagnostics are ignored (`ast-analyzer.ts:32`). Product honesty issues stack on top: `offlineVerified: true` is hard-coded (`store.ts:333`), any GitHub URL maps to the sample workspace with random stars and a fake SHA (`repositories/route.ts:46-65`), the 6 second Ollama timeout is shorter than a cold model load so users silently receive canned text presented as AI (`ghost-ai.ts:62`), and settings for temperature and sandbox timeout are ignored (`ghost-ai.ts:77`, `resurrection.ts:234`).

**Performance and persistence.** Every mutation, including each chat message and every report GET, rewrites the entire pretty-printed database synchronously (`store.ts:140-150,268,278,336`), and the database embeds full original and patched file contents. The write is non-atomic and unlocked, and `load()` swallows a parse failure and then overwrites the corrupt file with seed data, silently destroying user data (`store.ts:121-138`). The module-scoped singleton (`store.ts:353`) can diverge across Next route bundles and HMR. Synchronous `fs` calls block the event loop across `scanner.ts`, `resurrection.ts`, `files/route.ts` and `chat/route.ts`. Whole-file reads occur just to count lines (`scanner.ts:93`, `files/route.ts:50`), the chat route re-walks the tree on every message to use 15 files (`chat/route.ts:45-60`), and the scanner computes line numbers with `substring(0, idx).split('\n')` per match (`scanner.ts:274-275,314-315`), which is quadratic. File-walk logic is copied in five places and the dependency table has drifted between `scanner.ts` and `mastra/index.ts`.

**UI components.** `CodeExplorer` renders every line as a DOM node and runs `findings.find(... evidence.some ...)` per line on each render with no `useMemo` (`CodeExplorer.tsx:135-163`). Its fetch effects have no `AbortController` or `.catch`, so fast file switching can show stale content (`26-51`). Synthetic line numbers for `package.json` findings (`scanner.ts:157-158,208-210`) highlight arbitrary lines. `DiffViewer`'s "split" mode is not a diff at all: it prints the full original and patched files in two columns with no alignment or change highlighting, and `truncate` hides long lines (`DiffViewer.tsx:141-176`). It also recomputes `split('\n')` on every render and leaves the clipboard promise unhandled (`27,42-44`).

## Current best practice says upgrade Next, validate everything and use real Mastra

**Next.js.** Next 16.x is Active LTS, 15.x is Maintenance LTS and 14.x is "Unsupported" ([support policy](https://nextjs.org/support-policy)). The latest release is 16.4 (2026-10-06), which ships React 19.3 ([Next.js 16.4](https://nextjs.org/blog/next-16-4.md)). The Oct 14, 2026 out-of-band fix covered unauthenticated RCE in `use cache` functions, RCE in the Image Optimization API and a Server Actions DoS, and shipped only for 16.4.1 and 15.5.28 ([security update](https://nextjs.org/blog/nextjs-security-update-october-14-2026.md)). Next now follows a monthly security cadence, with another release planned for Nov 3, 2026 ([blog index](https://nextjs.org/blog)). Third-party trackers date 14.x end-of-life to October 2025 with a final 14.2.35 patch, but they disagree with the official page on 15's status ([HeroDevs](https://www.herodevs.com/blog-posts/nextjs-eol-dates-version-support-timeline)). Version 16 requires Node 20.9 or later and TypeScript 5.1 or later; removes synchronous `params`, `cookies()` and `headers()`, including `params` in route handlers; removes `next lint`; renames `middleware` to `proxy`; and makes Turbopack the default ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)). Codemods exist (`npx @next/codemod@canary upgrade latest`, `next-async-request-api`, `next typegen`) ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)). For this app, with a few `[id]` route handlers, no middleware and no custom webpack, the notes infer a small migration, though that cost estimate is unsourced and React 19 compatibility of third-party UI libraries was not checked. The guide also warns against enabling Cache Components or React Compiler merely to finish the upgrade. Because Next 14 cached GET route handlers that did not read the request, any such endpoint may be silently static in production today, and Next 15 reversed that default ([Next.js 15](https://nextjs.org/blog/next-15)). Pin `dynamic = 'force-dynamic'` and `runtime = 'nodejs'` meanwhile. Zod 4 is stable and brings `z.prettifyError` and `z.toJSONSchema()` ([Zod 4](https://zod.dev/v4)), and its adoption can be separate.

**Route handlers and security.** Treat every `route.ts` as a high-power entry point: validate params and bodies, authorize, return minimal DTOs and rate-limit expensive operations ([data security guide](https://nextjs.org/docs/app/guides/data-security)). Use `import 'server-only'` to keep server code out of client bundles, and keep secrets server-side. For paths, `path.join` and `path.resolve` do not confine a path to a base directory, so the resolved path must be checked against it ([Node path traversal guide](https://fooqux.com/article/2475)). The notes' recipe, which is an unsourced synthesis, is an allow-listed root, opaque repo ids instead of client paths, `realpath` containment using `rootReal + path.sep`, `lstat` walking, NUL-byte rejection and size caps. For long scans, return a `ReadableStream` response immediately rather than awaiting the loop ([route.js reference](https://nextjs.org/docs/app/api-reference/file-conventions/route)), with heartbeat and terminal `done` or `error` events. That SSE guidance rests on practitioner posts, not official docs ([DEV post](https://dev.to/richardlau/implementing-real-time-status-updates-with-server-sent-events-in-nextjs-4da1)), and abort detection is reported unreliable on Vercel ([Vercel thread](https://community.vercel.com/t/request-abortion-while-streaming-response-on-vercel/6071)). Archives, if ever accepted, are risky: OWASP does not recommend ZIP uploads and requires post-decompression size limits ([OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)). Safe git clone handling (shallow `execFile` with an argument array, HTTPS host allow-list, hooks disabled) is the notes' unsourced inference.

**Persistence.** The standard atomic-write pattern is write to a temp file in the same directory, fsync, then rename ([oauth-callback discussion](https://github.com/kriasoft/oauth-callback/issues/4)); `write-file-atomic` implements it but only queues writes within one process ([README mirror](https://chromium.googlesource.com/devtools/devtools-frontend/+show/0611f278abe052d949540e84bd85395ea792823a/node_modules/write-file-atomic/README.md)). The better fix is SQLite in WAL mode: `better-sqlite3` is on Next's auto-externalized list ([serverExternalPackages](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverExternalPackages)) and its README stresses WAL for performance ([README](https://app.unpkg.com/better-sqlite3@11.10.0/files/README.md)). Node's built-in `node:sqlite` is a release candidate since v25.7.0 ([Node docs](https://nodejs.org/api/sqlite.html)). Native modules need prebuilt binaries and fail on read-only serverless disks, which is an unverified inference. For a local-first lab, either option fits.

**Mastra, AST and LLM pipeline.** Mastra's current API is `createStep` and `createWorkflow(...).then()/.branch()/.parallel()/.commit()` with Zod or other Standard-JSON-Schema schemas, run via `createRun().start()` with a status of `success`, `failed`, `tripwire`, `suspended` or `paused` ([Mastra workflows](https://mastra.ai/docs/workflows/overview)). It offers step-level `retries`, workflow-level `retryConfig`, `bail()` and `onError` ([error handling](https://cdn.jsdelivr.net/npm/@mastra/core@1.51.0/dist/docs/references/docs-workflows-error-handling.md)), plus `suspend()` and `resumeData` with snapshots persisted to storage ([suspend and resume](https://mastra.ai/en/docs/workflows/suspend-and-resume)). Docs mix versions and show both `retries` and `retryConfig`, so verify against the installed `@mastra/core` types; the `.dountil` and `.foreach` signatures and the current version in October 2026 were not confirmed. For analysis, `createSourceFile` suffices for pure syntax, but semantic questions need one shared `Program` and `TypeChecker`, and `getPreEmitDiagnostics` returns unresolved-module errors (code 2307) that can replace the hand-rolled `existsSync` import checks ([Compiler API wiki](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)). Deprecation detection means resolving the symbol and reading its `@deprecated` JSDoc tag, as typescript-eslint's `no-deprecated` does ([rule](https://typescript-eslint.io/rules/no-deprecated/)). Text-matching `fs.exists` misses destructured and aliased imports and false-positives on any variable named `fs`; that is an inference. For LLM proposals, Claude structured outputs (`output_config.format` with `zodOutputFormat`) guarantee schema-valid JSON, but refusals and `max_tokens` stops can break the schema and changing the format invalidates the prompt cache ([structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)). Prompt caching needs at least a 512-token prefix on the 5.5-family models, and reads cost 0.05x on Sonnet 5.5 and Opus 5.5 ([prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)). The model-tiering advice (Haiku for triage and chat, Sonnet for patches, Opus for escalation) is the researchers' inference with no benchmark.

**React rendering.** TanStack Virtual v3 is the headless virtualization option ([TanStack Virtual](https://tanstack.com/virtual/latest)). `jsdiff` provides `structuredPatch` hunks, and its `timeout` and `maxEditLength` options return `undefined` instead of hanging on huge inputs ([jsdiff](https://github.com/kpdecker/jsdiff)). React Compiler is stable in Next 16 but off by default and slows builds ([upgrade guide](https://nextjs.org/docs/app/guides/upgrading/version-16)). No measured threshold for when a diff needs virtualization was found.

## The target design replaces the hub with a validated, sandboxed pipeline

The ideal design keeps the product shape (Autopsy, Ghost chat, Resurrection, Report) but changes what sits underneath. A Mastra workflow becomes the real spine: `discover`, then `staticDiagnosis` (AST plus manifest checks, run via `.parallel`), `reason`, `proposePatch`, `verify`, then a branch where a passing run finishes, a failure with attempts remaining loops through a bounded repair step of two or three iterations, and anything else calls `suspend()` for human approval. The suspend gate enforces the Ghost prompt's own rule that files are never modified without user approval. Per the notes, `repoPath` and `repoId` live in `stateSchema`, each step has a real Zod schema, LLM steps carry `retries: 2-3`, and the workflow is registered on a `Mastra` instance for tracing. If adopting Mastra is too heavy, the notes' minimum is to rename the class and add real `.parse` calls at stage boundaries, or to drop the Mastra claim from the README and DEV_SUBMISSION.

Analysis runs from one file inventory built once, feeding a single `ts.createProgram` with `allowJs`, `checkJs: false`, `noEmit`, `skipLibCheck` and explicit roots. Detectors are symbol-based, `getPreEmitDiagnostics` replaces manual import resolution, and `scanner.ts`' regex duplicates are deleted. `typescript` moves from devDependencies to dependencies if wired in (P9), and Next 15+ already auto-externalizes it. Per-file and total size and time budgets bound the cost of parsing untrusted repositories. Patching splits in two. Known patterns (`new Buffer`, `fs.exists`, `sys.puts`) get deterministic AST-range codemods, and `createCipher` is flagged non-mechanical because moving to `createCipheriv` requires key and IV design. Ambiguous cases go to an LLM that returns `{file, startLine, endLine, expectedOriginal, replacement, rationale, findingId}` through structured outputs, sending only the AST-extracted window rather than whole files. The server rejects any edit whose `expectedOriginal` does not match the file slice, whose finding id is unknown, or whose path escapes the root. The unified diff is generated server-side with `structuredPatch` and round-tripped through `applyPatch`. Before running tests, the pipeline re-parses the patched code, compares diagnostics against the baseline and re-runs the detectors to confirm each finding disappeared. Chat citations become structured `{file, lineStart, lineEnd}` objects verified against the evidence set, and the system prompt plus findings form a cached prefix. The reply states clearly when it comes from the canned fallback.

Execution is isolated. Baseline and patched runs both happen in a throwaway container, or at minimum a `fs.mkdtemp` directory with a scrubbed environment, `npm ci --ignore-scripts`, no network and CPU, memory and time limits, using `execFile` with argument arrays and `maxBuffer` handling. Imports resolve an opaque repo id to a path under an allow-listed root. Verification is opt-in. Persistence moves to `better-sqlite3` in WAL mode (or atomic temp-and-rename writes behind an in-process mutex as the cheap interim), a `globalThis`-cached handle, and no overwrite on parse failure. `.lastcommit_data.json` leaves git. All reads are side-effect free: scans run as jobs, started by POST and streamed or polled by GET. On the client, a `lab/[id]/layout.tsx` Server Component fetches once and hands data down, and only the explorer and diff panes are client components, with the diff viewer loaded through `next/dynamic`. The diff viewer computes hunks on the server, collapses unchanged regions, aligns split rows in one virtualized list and falls back to "file too large to diff" on timeout. The explorer flattens the tree, virtualizes both tree and lines, builds a per-line finding set with `useMemo` and cancels stale fetches with `AbortController`. The stack moves to Next 16.4.x on Node 22 or 24, with zod 4 as a separate step, ESLint configured directly because `next lint` is removed, and Vitest or `node:test` covering path traversal, engine-range parsing, patch transforms, store recovery and the verify route.

## Conclusion

The central finding is that the project's credibility gap and its safety gap share a root cause: the impressive-sounding layers (AST, Mastra, sandbox, offline verification) are the least real parts of the code, while the real parts (a regex scanner, a JSON file, a `/tmp` copy and `exec`) carry all the risk. That reframes the work. Wiring in the AST analyzer and a true workflow is not polish. It is what makes the product claims true, and the same restructuring (one inventory, one Program, validated edits, an isolated runner) removes most of the security surface. Doing it in the notes' order also front-loads cheap wins: roughly seven of the seventeen items are under an hour each.

Several points remain unverified and should be checked before relying on them. The audit never started the server, so the S1, S2 and S7 chain is from code reading. Page files (1,079 lines) were only grepped. The Mastra version current in October 2026, the TypeScript native-port impact on the compiler API, React 19 compatibility of dependencies, and the full npm advisory text were not confirmed. The model-tiering, SQLite-on-serverless and git-clone-hardening advice is inference without a benchmark or primary source. If the project will only ever run on a developer's localhost, items 1 to 5 drop in urgency but not in value, because the verify route executes whatever `test.js` the imported directory contains.
