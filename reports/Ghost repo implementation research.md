# Ship GHOST//REPO on JSON files

The GHOST//REPO plan holds up for a local-first Next.js 14 app, but it needs four corrections before implementation: poll with ETags and treat webhooks as optional, replace the single idle-days dormancy ladder with a multi-signal classifier, run the local model through a schema-constrained and code-verified evidence pipeline, and label every revival score as an unvalidated heuristic. The existing PAT tracker in `src/lib/github` is a sound base. A fine-grained read-only PAT, one serial worker and 5,000 requests per hour are enough for dozens of repos once conditional requests are added. The biggest gaps in the current code are that `client.ts` stores no ETags (a 304 would currently fall into the error path because `res.ok` is false), `classify.ts` uses idle-day cut points (30/90/180/365) that no published study uses, and nothing yet verifies model output against evidence. Evidence for revival potential is thin: one study found 41% of abandoned popular projects were later revived, and no study validates any score that predicts it. The plan document itself was not among the research notes, so this report verifies the plan's named capabilities (GitHub connection, activity sync, dormancy detection, local-AI summaries, cited resurrection plans) rather than its exact text. Facts below are tagged by source; claims marked as inference are design judgment, not documented behavior.

## Polling with ETags beats webhooks for a local app

**GitHub does not retry failed webhook deliveries, and receivers must answer 2XX within 10 seconds.** A laptop that sleeps will therefore silently miss events ([Handling failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries); [Best practices for webhooks](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)). The docs say never to use smee.io in production ([Testing webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/testing-webhooks)), and `gh webhook forward` is dev-only and allows one forwarder per repo at a time ([GitHub CLI forwarding](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/using-the-github-cli-to-forward-webhooks-for-testing)). If webhooks are offered at all, the verified recipe is: read the raw body with `await req.text()` (an inference for Next.js route handlers), compute HMAC-SHA256 with the secret, compare `X-Hub-Signature-256` using a constant-time comparison, and dedupe on `X-GitHub-Delivery`, which stays the same on redelivery ([Validating deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)). GitHub publishes a test vector (secret `It's a Secret to Everybody`, payload `Hello, World!`) that makes a good unit test. My recommendation is polling as the default and webhooks as an opt-in accelerator that also triggers a reconciliation poll.

Polling is nearly free if it is conditional. Sending `If-None-Match` with a stored ETag returns 304, and **an authenticated 304 does not count against the primary rate limit** ([REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). ETags change with any parameter or page change, so the tracker should key stored ETags by the exact URL and conditionally check only page 1. The Events API is built for ETag polling and returns an `X-Poll-Interval` header to obey, but it holds only 300 events from the last 30 days and has 30 second to 6 hour latency ([Events API](https://docs.github.com/en/rest/activity/events)). That makes it a hint for "something changed", not a source of truth. For truth, keep the existing `GET /repos/{o}/{r}/commits?since=` approach, which the docs confirm accepts `since` and `per_page` up to 100 ([Commits API](https://docs.github.com/en/rest/commits/commits#list-commits)). The pulls list has no `since` parameter, while the issues list has `since` and also returns PRs, which you must filter by the `pull_request` key ([Pulls](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests); [Issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues)).

Concrete changes to `client.ts`, all inference from the verified facts above. Add an `etags: Record<string,string>` map to the JSON db and send `If-None-Match`. Return a `{notModified: true}` result on 304 instead of throwing. Persist `lastModified` beside it and honor `X-Poll-Interval` when the Events endpoint is used. Keep the existing behavior of reading `retry-after` and `x-ratelimit-reset`, which matches GitHub's documented backoff order: wait `retry-after` if present, else until reset if remaining is 0, else at least a minute ([Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Note the current code throws on any 403 with `retry-after` over 60 seconds, which is acceptable if the scheduler then sleeps until `resetAt`. The REST version header should move deliberately: the default is `2022-11-28` (supported until 2028-03-10) and `2026-03-10` is the latest ([API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions)), so pinning the older value is safe for now. Limits that matter at this scale: 5,000 requests per hour for a PAT, 100 concurrent requests and 900 REST points per minute as secondary limits, so one serial worker is the simplest compliant design ([Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). A fine-grained read-only PAT is the right default for a self-hosted tool; GitHub recommends Apps for long-lived integrations and calls PATs suited to scripts and testing ([Deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)). An App with device flow is a later upgrade, but its user tokens still share the user's 5,000 per hour pool ([Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)), so it buys no capacity without installation tokens and a locally stored private key.

Two cautions on the stats endpoints, which are attractive for activity histograms. They return 202 while computing and must be retried later, and `code_frequency` returns 422 for repos with 10,000 or more commits ([Repository statistics](https://docs.github.com/en/rest/metrics/statistics)). Use `stats/participation` (52 weekly counts, owner versus all) only as an optional extra, give up after a couple of attempts, and retry on the next scheduled cycle. Whether ETags work on stats endpoints is undocumented in the notes. Likewise, GraphQL aliasing to batch many repos per query is standard GraphQL but no GitHub page demonstrating it was found; the verified limits are 5,000 points per hour, 500,000 nodes and `first` between 1 and 100 ([GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). Treat GraphQL as an optimization to add only if REST proves too chatty, since REST plus ETags already fits the budget.

## Dormancy needs tiers and human signals, not one idle counter

The current `classify()` bands (30, 90, 180, 365 days) are reasonable for a dashboard but do not match any published definition of abandonment, and the literature is blunt that no universal threshold exists. OpenSSF Scorecard's Maintained check uses a 90-day window and scores commits plus issue updates against a target of about 12, with archived repos forced to the minimum ([Scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md); [maintained.go](https://raw.githubusercontent.com/ossf/scorecard/main/checks/evaluation/maintained.go)). Academic definitions are longer: no commits for a year ([Coelho 2017](https://arxiv.org/pdf/1707.02327)), a developer "gone" after one year ([Avelino 2019](https://arxiv.org/pdf/1906.08058.pdf)), and two years of zero contributor activity after two years of regular maintenance for npm packages, which gave "almost perfect precision" while a looser rule of about three commits a year mixed in feature-complete packages ([Miller et al. 2025](https://cmustrudel.github.io/papers/icse2025abandonment.pdf)). An ML study found the single strongest predictor was commit volume in the most recent interval and explicitly rejected a fixed gap as arbitrary ([Coelho 2018](https://ar5iv.arxiv.org/html/1809.04041)).

The practical refinements, each grounded in those sources, follow. First, stop relying on `pushed_at`, which moves on any branch push, and use dates of human-authored commits on the default branch; the existing `listCommits` call already takes a branch, so filter out `[bot]` logins and known automation (Dependabot, Renovate) before computing `lastHumanCommit` ([GitHub community discussion](https://github.com/orgs/community/discussions/24442); Miller et al. handle bot commits explicitly). Second, add a declared-state check for a README notice, but only as a flag requiring confirmation: a keyword match on deprecation phrases had just 37% true positives after manual review ([Coelho 2017](https://arxiv.org/pdf/1707.02327)). Third, separate "finished" from "abandoned" using maintainer responsiveness, because commit silence alone cannot distinguish them and the literature admits no clean separator ([Miller et al. 2025](https://cmustrudel.github.io/papers/icse2025abandonment.pdf); [Avelino 2019](https://arxiv.org/pdf/1906.08058.pdf)). A proposed rule, which is my synthesis and not a published standard, is to label a repo abandoned at 24 or more months without human default-branch activity, dormant at 12 to 24, slowing at 3 to 12 with low activity, "declared" when a notice is confirmed, and "complete?" when old but with few open issues and no unanswered recent ones. Archived stays its own terminal state, and GitHub confirms archiving is reversible ([Archiving repositories](https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories)). The existing JSON-stored `ActivityStatus` can carry these as additional enum values without a migration beyond bumping `version`.

For the resurrection score in `resurrectionScore()`, the present formula (log of stars and forks, times idle years capped at 4) rewards long idleness, which the evidence contradicts. Revival is concentrated early: of 315 abandoned projects, 41% survived through new core developers, **64% of those within the first year** and 23% in the second, and survivors were mostly revived by former contributors (52%) motivated by their own use ([Avelino 2019](https://arxiv.org/pdf/1906.08058.pdf)). Departed core developers return only about 21 to 26% of the time after a break of a year or more ([Calefato 2022](https://arxiv.org/abs/2103.04656)). So the score should peak for repos idle roughly 6 to 24 months and decay afterward, not climb. No study validates any weights for stars, tests, CI or dependents as predictors of revival success; the notes found none. The score should therefore be shown as a transparent breakdown (value, feasibility, penalties) labeled "heuristic", never as a probability. Useful inputs that are cheap to fetch are license presence, CI config, open issue counts, and an active fork check (an active fork outcommitting upstream means revival already happened, an inference). Dependents counts are not in the REST or GraphQL APIs per the notes, so treat them as an optional external lookup.

## Local summaries need schema, evidence IDs and code-side verification

Ollama supports a JSON Schema in the `format` field of `/api/chat`, with `stream: false` and options like `temperature`, `seed`, `num_ctx` and `num_predict` ([Chat API](https://docs.ollama.com/api/chat); [Structured outputs](https://docs.ollama.com/capabilities/structured-outputs)). The documented JS pattern is `z.toJSONSchema(schema)` for the request and `schema.parse(...)` on the response, and the docs advise also describing the schema in the prompt ([Structured outputs](https://docs.ollama.com/capabilities/structured-outputs); [Zod JSON Schema](https://zod.dev/json-schema)). Two traps are verified. Context defaults to 4k tokens on machines with under 24 GiB of VRAM, so a long history is silently cut unless context is raised ([Context length](https://docs.ollama.com/context-length)); compare `prompt_eval_count` against the configured `num_ctx` to detect truncation ([Chat API](https://docs.ollama.com/api/chat)). And structured output is not enforced on Ollama's cloud per the docs ([Structured outputs](https://docs.ollama.com/capabilities/structured-outputs)), so the app should call only the local endpoint. Model choice is unbenchmarked for this task: the notes found no head-to-head commit-summarization comparison. Verified candidates are `qwen3:8b` (5.2 GB), `qwen3:4b` (2.5 GB, 256K context), `gpt-oss:20b` (14 GB, 128K context, structured output listed) and `gemma3:4b/12b` ([qwen3](https://ollama.com/library/qwen3); [gpt-oss](https://ollama.com/library/gpt-oss); [gemma3](https://ollama.com/library/gemma3)). Reported structured-output problems with gpt-oss come from a single blog ([glukhov.org](https://www.glukhov.org/llm-performance/ollama/ollama-gpt-oss-structured-output-issues/)), and thinking models combined with `format` have had issues, so setting `think: false` and running a quick local test per model is prudent (inference). Make the model name a setting with a small default and surface a clear "Ollama not running" state.

Grounding is where the plan most needs rigor, and here the notes provide design, not benchmarks. A sound pipeline, all inference: build numbered evidence items (`E12` commit with SHA and date, `E40` README excerpt, `E77` issue number); build the Zod schema per request with `z.enum` of the exact supplied IDs so invented IDs cannot validate; require each claim to carry a `status` of confirmed, inferred or unknown, one or more `evidence_ids`, and a verbatim `quote`; then in code check that every ID exists and the quote is a whitespace-normalized substring of the cited item, downgrading or dropping claims that fail. Compute confidence in code from verified quotes rather than trusting the model's number. The notes did not verify that large enum lists work in Ollama's grammar converter, so test that early. For long histories use map-reduce with chunks of roughly 2 to 4k tokens and have the reduce step see only validated claims. Exclude lockfiles, build output, binaries and any file with a secret hit, and prefer README, manifests, CI config and commit subjects over full diffs. Resurrection plans should be built the same way: each step cites evidence IDs, and steps without evidence are shown as "suggested" rather than "found".

Prompt injection deserves explicit design because repo text is attacker-controlled. OWASP says there may be no fool-proof prevention and recommends output-format validation in code, input and output filtering, least privilege and human approval for high-risk actions ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). Spotlighting cut attack success from over 50% to under 2% in the authors' experiments ([Hines et al.](https://arxiv.org/abs/2403.14720)), but adaptive attacks bypassed 12 published defenses at 71 to 100% success ([Nasr, Carlini et al.](https://arxiv.org/abs/2510.09023)), and Willison considers delimiters and detector LLMs "tried and found lacking" while endorsing a quarantined model with no tools whose output goes to non-LLM code ([Willison](https://simonwillison.net/2023/Apr/25/dual-llm-pattern/)). Applied here, the summarizer call gets no tools, its output is rendered as plain text (never as links or images), and no action is taken from model text. Be honest in the UI that quote verification catches fabrication but not a true quote used misleadingly. Redact secrets before prompting and logging. The regex patterns for AWS keys, GitHub tokens and private key headers in the notes come from memory rather than a fetched source, so validate them against test strings; Gitleaks can read stdin if installed, though its README says it is in maintenance mode ([gitleaks](https://github.com/gitleaks/gitleaks)).

## Persistence and scheduling inside the JSON store

None of the notes covers Node-side persistence, so this section is engineering inference grounded in the repo as inspected. `db.ts` holds the whole database in memory on `globalThis` and writes it atomically through temp file and rename, quarantining corrupt files, which is a good pattern for a single process. Additions fit it with small schema growth: an `etags` map, a `summaries` map keyed by repo and a hash of the evidence set (so unchanged repos never re-run the model), a `deliveries` ring buffer of recent webhook GUIDs, and per-repo `dormancy` details including the signals used. Cap and prune as `MAX_EVENTS` already does, and keep model output out of the main file if it grows large by writing one JSON file per repo summary. Because `saveDb` rewrites the whole file, avoid saving inside tight loops; save once per repo sync. The in-process `setInterval` in `service.ts` is adequate if guarded against overlapping runs and if it runs a catch-up sync at startup, since a sleeping laptop skips ticks. Run LLM summarization as a separate queued job after sync with concurrency of one, because Ollama on a laptop is the bottleneck. Next.js dev reloads can duplicate timers, which the existing `globalThis` guard (`__trackerTimer`) already addresses.

## Conclusion

The plan's weakest link is not engineering but epistemics. Dormancy has defensible, sourced definitions that favor a tiered, human-signal classifier over idle days, whereas "resurrection potential" has no validated predictor at all, and the one robust empirical fact is that revival odds fall quickly after the first year or two. The product should say so, ranking recently dormant repos with real demand above ancient ones and presenting the score as an explainable heuristic.

The second implication is that citations should be mechanical, not aspirational. Because small local models can produce schema-valid fiction, the guarantee users can trust comes from code that checks IDs and quotes against fetched GitHub data, which also makes the whole feature testable without Postgres, Redis or any hosted model. Open items worth a spike before committing are the Ollama grammar behavior with large ID enums, the chosen model's reliability with `format`, and whether ETag handling on pages beyond the first behaves as the docs imply.
